# 审核、反垃圾与通知

> 状态：规划草案，经独立审阅修订；§3.4 的数值在 C2 内测后回填 · 最近更新：2026-09-26
> 表结构见 [data-model.md](data-model.md)，接口见 [api.md](api.md)。

---

## 1. 原则

1. **博主管自己站点的评论，平台管越界的事**。越界指违法内容、跨站滥用和站点本身的问题。
2. **对登录读者宽松，对访客谨慎**。登录读者有持续的身份，出了问题可以按账号封禁；访客只有一次性的昵称和邮箱。
3. **不用第三方反垃圾服务**。Akismet 这类服务要把评论内容和读者信息发给第三方，在国内也不稳定。反垃圾只用自己的规则、限流和工作量证明。
4. **自动判断都能被推翻，也都有记录**。系统判成垃圾或待审的评论，管理者可以恢复；每一次处置都写进 `moderation_events`。
5. **评论属于写它的人**。管理者可以隐藏评论，不能改写别人的评论。

## 2. 发布规则

新评论按顺序检查，第一条命中的决定结果：

| # | 条件 | 结果 |
|---|---|---|
| 1 | 站点不是 `active`，讨论页已锁定，或已到自动关闭的时间（[sites.md §4](sites.md#4-站点设置与讨论页管理)） | 拒绝：「评论已关闭」 |
| 2 | 作者的账号被暂停，或在本站、全网被封禁（账号、访客邮箱、IP 任一命中） | 拒绝：「你无法在此发表评论」，不说明原因 |
| 3 | 访客评论，但站点 `guest_policy = off` | 拒绝 |
| 4 | 超出 §3.4 的限额（包括新建讨论页的频率） | 拒绝，返回 `429` 和 `Retry-After` |
| 5 | 命中 §3.1 的垃圾规则 | 保存为 `spam`；作者看到的和待审一样，是「已提交，审核通过后显示」 |
| 6 | 命中站点屏蔽词，或新账号（§3.3）发了链接 | `pending` |
| 7 | 访客评论且 `guest_policy = review`，或登录读者且 `member_policy = review` | `pending` |
| 8 | 其余 | `published` |

之后的流转：

- 管理者：`pending` → `published`、`hidden`、`spam`；`published` → `hidden`、`spam`；`hidden`、`spam` 在保留期内可以恢复成 `published`（[data-model.md §4](data-model.md#4-保留期)）。
- 作者：随时可以删除自己的评论（→ `deleted`）；在编辑窗口内（§3.4）可以编辑。编辑后的评论重新走第 5–7 条：命中第 5 条改为 `spam`；命中第 6 条，或站点对这类作者先审后发（第 7 条），退回 `pending`。否则在先审后发的站点上，通过审核的评论可以被改成任何内容而保持公开。编辑前的版本按保留期保存。
- 只能回复已发布的评论。
- 评论数、回复通知和站长通知都只在评论变成 `published` 时触发。

## 3. 反垃圾

### 3.1 通用规则

- 长度和链接数超出 §3.4 的上限，直接拒绝。
- 同一作者 10 分钟内发出相同正文，拒绝为重复。
- 相同正文 1 小时内出现在 3 个以上站点，判为垃圾。
- 链接指向平台维护的垃圾域名清单，判为垃圾。
- 显示名和访客昵称去掉零宽字符和双向控制字符，防止伪装成别人的名字。

### 3.2 访客

- **工作量证明**：组件先取一道题（`GET /api/v1/pow/challenge`），在 Web Worker 里算 SHA-256 前缀，普通手机约 1 秒；同一 IP 发得越频繁，题越难。解随评论一起提交，服务端校验后记入 `pow_spent`，一个解只能用一次。协议参考开源的 ALTCHA。不用第三方验证码服务：它们要加载第三方脚本、收集读者信息，在国内也常常打不开。
- 昵称、邮箱必填，网址可选；表单另有一个对人不可见的蜜罐字段。
- 访客不能编辑、删除自己的评论，因为没有身份可以验证。
- 站点是否接受访客、要不要先审后发，由博主在新建站点时明确选择（[sites.md §4](sites.md#4-站点设置与讨论页管理)）。

### 3.3 登录读者

- **新账号**：注册时间短于 §3.4 的「新账号」时长。新账号带链接的评论先进审核（§2 第 6 条）。
- **可信账号**：同时满足 §3.4 的「可信账号」条件：注册够久；在自己既不拥有也不协管的站点上，已有足够多条已发布的评论，而且分布在不止一个站点；没有被处置过。只数别人站点上的评论，是因为开放注册以后，谁都能建个站点给自己刷评论。可信账号不受新账号规则限制，它们的举报才计入 §4.3 的自动退回。

### 3.4 限额 `[待定]`

数值只写在这里，代码常量在 `internal/policy`。先按下表上线，C2 内测后按实际数据回填。

| 项 | 值 |
|---|---|
| 评论长度 | 5,000 字符（按 Markdown 原文计） |
| 每条评论的链接数 | 5 |
| 新建讨论页 | 每个账号每小时 5 个；访客同一 IP 每小时 3 个 |
| 新账号 | 注册未满 24 小时 |
| 可信账号 | 注册满 7 天；在别人的站点上有 3 条以上已发布评论，分布在至少 2 个站点；没有被处置过 |
| 登录读者发表 | 每站点每分钟 3 条；全网每 10 分钟 20 条 |
| 访客发表 | 同一 IP 每 10 分钟 5 条 |
| 编辑窗口 | 发表后 24 小时 |
| 举报 | 每人每天 30 次 |
| 认领验证邮件 | 每账号每小时 3 封 |
| 访客邮箱确认信 | 每个邮箱每天 1 封 |
| 站点验证 | 每站点每小时 10 次 |
| 每个站点的别名 origin | 5 个 |
| 每个站点的屏蔽词 | 200 个 |
| 计入讨论页标识的查询参数 | 5 个 |
| 导入文件 | 50 MB |
| 建登录交易 | 每 IP 每分钟 10 次 |
| 兑换登录（轮询） | 每 IP 每分钟 120 次 |
| 匿名读取 | 每 IP 每分钟 300 次 |

限流在进程内存里按固定窗口计数，和 Explore 相同。服务是单实例，这样就够了；以后多实例时再挪到 PostgreSQL 或 Redis。

## 4. 审核与处置

### 4.1 站点管理者

站点所有者和协管员在控制台里操作；单条评论的通过、隐藏、恢复、置顶、标为垃圾也可以在自己站点的组件里直接做，封禁和批量处理只在控制台里（[api.md §5](api.md#5-组件写入与管理者读取)）。

- **队列**：待审核、被举报、垃圾、全部；可按讨论页筛选；支持批量通过、隐藏、标为垃圾。
- **单条操作**：通过、隐藏、标为垃圾、恢复、置顶、取消置顶。
- **讨论页**：锁定、解锁；迁移或合并到另一个标识（[sites.md §4](sites.md#4-站点设置与讨论页管理)）。
- **封禁**：按账号、访客邮箱或 IP，范围是本站点，可以设期限。IP 封禁记下的是封禁当月密钥算出的 `ip_hmac`；检查时用当月和上个月的密钥各算一次请求 IP 的 HMAC 去比对，所以 IP 封禁在建立的当月和下个月有效，到期自动失效。IP 本来就常变，长期封禁应该按账号或邮箱。
- **能看到的读者信息**：显示名、个人主页、访客填写的邮箱（访客是在这个站点留下的邮箱）。登录读者的邮箱不对博主公开。

### 4.2 平台

平台维护者负责：

- 理由为「违法」「隐私」的举报。这两类举报同时进入站点和平台两个队列。
- 跨站滥用：全网封禁账号，必要时在身份服务上停用账号。
- 站点问题：暂停站点（`suspended`），比如用评论区发布违法内容、冒充他人博客。
- 发到 `abuse@kite.plus` 的投诉和删除请求。

平台的处置同样写进 `moderation_events`，站点管理者在控制台看得到。违法内容的处理时限 `[待定]`，上线前写进服务条款。

### 4.3 举报

- 只有登录读者能举报，访客不能，避免被刷。
- 理由：垃圾广告、人身攻击或骚扰、违法、泄露个人信息、其他，可附 500 字说明。
- 同一条评论被 3 个不同的、满足 §3.3 信任条件的账号举报，自动退回 `pending`，等管理者处理 `[待定]`。

### 4.4 处置记录

`moderation_events.action` 的取值：

| 类别 | `action` |
|---|---|
| 管理者 | `approve`、`hide`、`spam`、`restore`、`pin`、`unpin`、`lock`、`unlock`、`move_thread`、`ban`、`unban` |
| 系统 | `auto_spam`、`auto_pending`、`auto_close`、`report_threshold` |
| 平台 | `platform_hide`、`platform_suspend_site`、`platform_ban` |
| 作者 | `author_edit`、`author_delete`、`claim` |

`detail` 记录判断依据（命中的规则、举报 ID、封禁期限），不存评论正文。

## 5. 内容格式

读者写 Markdown，服务端渲染并净化成 HTML 后保存；组件只插入服务端给的 HTML，不在浏览器里渲染 Markdown。

- **支持**：段落、换行（单个换行即换行）、粗体、斜体、删除线、行内代码、代码块、引用、列表、链接和自动链接。
- **不支持**：图片（显示成链接）、标题（显示成粗体段落）、表格、脚注、原始 HTML（原样转义）。
- **链接**：只允许 `http`、`https`、`mailto`；一律加 `rel="ugc nofollow noopener noreferrer"` 和 `target="_blank"`。
- **表情**：只有 Unicode emoji。不做表情包：图片的托管、审核和版权都是负担。
- **代码高亮**：C2 不做；C3 再决定是否用 chroma 在服务端输出高亮 `[待定]`。
- **实现**：goldmark 渲染（关闭 unsafe），再用 bluemonday 按白名单净化。渲染或净化规则改了，`render_version` 加一，由 worker 在后台重渲染旧评论。

不支持图片是有意的：评论里的外链图片会把读者的 IP 泄露给第三方，也可以用来追踪；自己托管图片，又要承担审核违法图片的责任。C4 之后再评估。

## 6. 通知

### 6.1 读者

- **回复通知**：登录读者的评论收到回复（回复已发布、不是自己回复自己、这个讨论页没被关闭通知）时，在读者中心生成一条通知；开启了邮件通知的，同时发邮件。同一读者 10 分钟内的多条回复合并成一封（`outbox.coalesce_key`，[data-model.md §3.6](data-model.md#36-通知访客邮箱与认领)）。每封邮件里可以关闭这个讨论页的通知。
- **访客**：访客勾选了「有人回复时通知我」，这个邮箱第一次出现时只发一封确认信，确认后才发通知，同样合并发送，每封都带退订链接。访客没有读者中心，只有邮件；退订按邮箱整体生效。未确认的邮箱按保留期删除。这样没人能用别人的邮箱留言，让对方收到骚扰邮件。
- **邮件里的链接只打开页面**：确认、退订、关闭讨论页通知，都要在打开的页面上点按钮（POST）才生效。邮件网关会自动打开邮件里的链接做安全扫描，链接本身生效的话，确认信就形同虚设（[api.md §9](api.md#9-回调与其他)）。RFC 8058 的一键退订本来就是 POST，照常支持。
- **内容**：站点名、文章标题、回复者的显示名、回复的前 200 字（纯文本）、带 `#kc-` 锚点的链接。不支持用邮件回复。
- **语言**：登录读者按账号设置，访客按留言时组件的语言。

### 6.2 博主

- 站点有新的已发布评论或待审核评论时通知所有者，频率按站点设置：即时（和回复通知一样合并发送）、每日汇总、关闭。合并和汇总按 `site_members.last_notified_at` 记录上次发送的时间。每日汇总的发送时间 `[待定]`。
- 「违法」「隐私」类举报无论设置如何都即时通知。

### 6.3 发信

- 所有邮件经 `outbox` 由 worker 发送，失败按指数退避重试，最多 8 次。
- 发件人 `Kite Plus 评论 <notify@kite.plus>`；`kite.plus` 配好 SPF、DKIM 和 DMARC，否则 QQ 邮箱、163 邮箱很可能直接拒收。
- 通知邮件都带 `List-Unsubscribe` 和 `List-Unsubscribe-Post`（RFC 8058），支持一键退订。
- 纯文本和简单 HTML 两个版本，中英两套模板。
- 不加追踪像素，不改写链接做点击统计。
- 退信处理：硬退信的地址停止发送，需要发信服务商的回调 `[待定]`。
